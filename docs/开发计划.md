# 开发计划

依据 `docs/项目背景.md`（讨论 #2）整理，并按参考实现的源码核对过一遍
（2026-09-11，见该文件的「与参考实现核对后的更正」）。本文件是计划的事实源；
里程碑勾选在 issue 里维护。

## Scope 评估

**中小型（M），但上限取决于一个前提**：如果 Linux 版 WeChat 的视频号仍然走
`channels.weixin.qq.com` 那个 webview H5 页面，那么 2–3 周零散投入可以拿到「能用」的
版本 —— 参考实现已经把机制走通了，我们只是换个语言 + 补上 Linux 的代理与 CA 部分。

如果 Linux 客户端是原生渲染视频号，参考实现的注入路线**整条失效**，`decode_key` 得另找
来源，那就不是 M 而是一个逆向项目，需要重新评估要不要做。

代码本身没有难点，风险集中在两处未知：

1. **Linux 版 WeChat 能不能被 MITM** —— 代理怎么设、CA 怎么让它信任。参考实现只有
   Windows（注册表）和 macOS（`networksetup`）两条路，Linux 没有代码可借。
2. **Linux 客户端的视频号是不是同一条 H5 路径** —— 有没有可注入的页面、有没有
   `window.WeixinJSBridge` 可以 hook。这是决定项目性质的那个问题。

### 已经不再是未知的部分

- **`decrypt.js` 可以脱离 Electron 复用** —— 已实测：纯 Node v24 里 import 即用，
  wasm 以 base64 内嵌在文件里，无需 Electron、无需额外 .wasm 文件。
- **它到底做什么** —— ISAAC64 keystream 生成器：`getDecryptionArray(seedString)` 返回
  131072 字节，用来 XOR 掉下载文件的**前 128 KiB**。它不解析下载地址；地址直接来自
  JSAPI 响应的 `url + url_token`。
- **两个坑** —— seed 必须以字符串传（wasm 侧是 `std::string`，传 number 直接抛错）；
  `decode_key` 是 64 位整数，被当成 JS number 解析会静默丢精度、keystream 完全错位。

## 是否需要 specs：先不写，先做 spike

**建议现在不写完整 specs**，先用 1–2 天做 M0 spike 把上面两处未知打掉。spike 结束后：

- 两处都通了 → 直接按里程碑推进，本计划 + `docs/项目背景.md` 里的协议记录当设计文档就够了；
- Linux 客户端不走 H5 / 没有 bridge → 停下来重新评估，这时才值得为「怎么拿到
  `decode_key`」单独写一份 `docs/specs/decode-key.md`（需求 + 设计 + 可行性）。

理由：这个项目的成本不在写代码，而在摸清 Linux 客户端的行为；在摸清之前写出来的设计
大概率要重写。参考实现的机制已经读明白了，不需要再为它写规格。

## 里程碑

### M0 — spike：打通 Linux 侧可行性（最先做，1–2 天）

工具侧已经就绪（`wxclip proxy` / `wxclip ca` / `web/inject.js`，操作步骤见
`docs/M0-操作步骤.md`），剩下的都是要真人在 WeChat 里操作才能验的：

- [x] 让 Linux 版 WeChat 走本机代理：**应用内代理设置可用**（issue #4 的截图）
- [x] 代理与 CA 落地：mitmproxy + 自签 CA（`~/.config/wxclip/ca/`），注入与回传通道已在
      真实 TLS 上验证（`channels.weixin.qq.com` 能被 MITM 出明文；注入与
      `/__wxclip/*` 端点用 curl 走通）
- [x] 让 WeChat 信任这张 CA：**只有主进程做得到**。装进 Flatpak 沙箱的 NSS 库后主进程接受本地
      证书、HTTPS 解出明文（2026-09-11 实测，无一次 TLS 失败）；**webview 靠装 CA 永远不行**，
      它的根证书编译在 `WeChatAppEx` 二进制里，做校验的进程从不打开 NSS 数据库
      （证据见 `docs/项目背景.md`）
- [x] **H5 路线是否存在**：成立。webview 打开的就是
      `channels.weixin.qq.com/web/pages/feed?oid=…&nid=…`（标题「视频号」），URL 与参考实现一致
- [x] **把 webview 也塞进代理**：`flatpak override --env=http_proxy=…` 可行，webview 确实来连
      代理（桌面图标/托盘启动走 systemd app scope，`flatpak run --env=…` 对它无效）
- [x] **让 webview 接受我们的证书**：唯一的路是给它加
      `--ignore-certificate-errors-spki-list=<base64(sha256(SPKI))>`（只放行我们这一个公钥）。
      它的命令行由 `libwmpf_host_export.so` 拼、不读环境变量，所以用 LD_PRELOAD 在 exec 时插进去
      （`scripts/appex-flags-preload.c` + `scripts/build-appex-preload.sh`）。
      **已生效**：switch 进了 browser 与 NetworkService 两个进程的 cmdline，页面正常打开
- [x] 页面经过代理后，确认注入生效、`window.WeixinJSBridge` 存在且可 hook：`probe` 里
      `has_bridge: true`/`hooked: true`，`hook` 里 `has_invoke: true`/`has_on: true`
- [x] 抓一次真实的 JSAPI 响应：api 是 `finderH5ExtTransfer`（同 macOS）、`err_msg` 是
      `H5ExtTransfer:ok`（同 Windows），`decode_key` 是**带引号的字符串**、8–10 位十进制
      （不是 20 位）。脱敏样本进了 `evals/jsapi-response-linux-20260911.md`
- [x] 用 Node 跑 `decrypt.js` + 真实 `decode_key`，手工 XOR 前 128 KiB：产出的 mp4 能播
      （`tools/m0-download-decrypt.mjs`，h264 1080x2344 + aac 7.48s，`ffmpeg -f null -` 零报错）
- [x] 把结论写回 `docs/项目背景.md` 的「待确认的前提」，并更新本计划

**退出标准 —— 已达成**（2026-09-11）：手工串起来下载并解密出了一个可播放的视频文件。
注入路线在 Linux 上成立，前提是给 webview 加上那个 spki switch。

### M1 — CLI 端到端

- [ ] `wxclip proxy` —— 启动 MITM 代理，注入脚本，接收回传的 `decode_key` + URL
- [ ] `wxclip download <url> --key <decode_key>` —— 直连下载（不走代理）+ XOR 解密
      前 128 KiB，支持断点续传
- [ ] `wxclip decrypt <file> --key <decode_key>` —— 对已下载的密文文件单独解密，
      便于排查和重跑
- [ ] `wxclip capture` —— 一条命令完成「注入 → 抓 key → 下载 → 解密」
- [ ] keystream 来源二选一：Node 子进程调 `decrypt.js`，或把 ISAAC64 移植进 Python
      （用 `decrypt.js` 的输出做黄金样本比对）
- [ ] pytest 覆盖：JSAPI 响应解析、keystream 一致性、XOR 边界（文件小于 128 KiB、
      正好 128 KiB、大于 128 KiB）、`decode_key` 全程字符串不丢精度

**退出标准**：一条命令从播放到可播放文件，`make lint test` 通过。

## 技术选型（M0 后定稿）

| 环节 | 候选 | 取舍要点 |
|------|------|----------|
| MITM 代理 | **已定：`mitmproxy`**（optional 依赖 `.[proxy]`） | 能改写响应体、自带 CA 管理与 flow 存档；`wxclip.proxy` 只是一个 addon，mitmproxy 延迟导入，测试与 CI 不依赖它 |
| CA 信任 | 系统 CA 目录 / NSS / 客户端自带校验 | 本机 WeChat 是 Flatpak：宿主机 `update-ca-trust` 它看不到（runtime 自带证书包），webview 是 Chromium 内核、用 NSS 库。`scripts/trust-ca.sh` 三个位置都覆盖，哪个生效 M0 验 |
| keystream | Node 子进程跑 `decrypt.js` / 移植 ISAAC64 到 Python | 先桥接跑通（注意运行时异步初始化、seed 传字符串），再决定要不要移植掉 5.2 MB 的 Node 依赖 |
| 下载 | `httpx` / `aria2c` | 要能断点续传；解密只影响前 128 KiB，续传要记住已解密的偏移 |
| web server | `fastapi + uvicorn` / stdlib | 面板很薄，别为它引入大框架 |
| 截屏/提取 | `ffmpeg` + OCR 引擎 | 是否需要本地模型、是否要 GPU |

## 边界

见 `AGENTS.md` 的 Boundaries：仅限本人客户端已可播放内容的个人使用；不做付费/受限内容的
DRM 破解、不做他人账号批量抓取、不再分发抓取到的媒体。

## 已定下来的实现细节

这几条是写代理时定的，和参考实现有意不同，理由记在这里免得以后当成 bug 改回去：

- **注入脚本走页面同源**：`<script src="/__wxclip/inject.js">`，代理拦下 `/__wxclip/*`
  自己回，不转发上游。参考实现从 `res.wx.qq.com` 取脚本、往哨兵域名 `aaaa.com` 回传，是为了
  绕页面 CSP；同源既满足 `script-src 'self'`，回传也不触发 CORS 预检。注入时同时删掉响应的
  CSP 头作为双保险。
- **`decode_key` 用正则从响应原文里抠**：`/"decode_key"\s*:\s*("?)(\d{1,20})\1/`。
  只要经过 `JSON.parse`，裸数字形式的 key 就已经是 float 了（`13835058055282163712` →
  `13835058055282164000`），而且不报错。引号有没有一并记成 `decode_key_json_type`，正好是 M0
  要回答的问题之一。`tools/check-inject.mjs` 专门守着这条。
- **默认不 MITM `(long|short|minorshort|dns).(wechat.com|weixin.qq.com)`**：那是 mmtls，不是
  TLS，让它原样穿过，别把登录搞坏（`--ignore-host` 可改）。本机客户端用的是 `*.wechat.com`
  那半边 —— 第一轮只挡了 `*.weixin.qq.com`，结果 276 个 mmtls 请求被白拦，视频也没播出来。
- **给 webview 加 Chromium switch 靠 LD_PRELOAD**：`scripts/appex-flags-preload.c` 钩
  `execv`/`execve`/`execvp`/`posix_spawn`，只对程序名匹配 `WXCLIP_APPEX_TARGET`（默认
  `WeChatAppEx`）的 exec 追加 `WXCLIP_APPEX_FLAGS` 里的参数，已在 argv 里的 switch 不重复追加
  （Chromium 会 re-exec 自己拉子进程）。.so 放在 `~/.var/app/<app-id>/.wxclip/`
  并 `--persist=.wxclip`，沙箱里才看得见。
- **spike 期间日志开得很大**：每条 flow 的摘要、注入前的原始页面、以及注入脚本看到的**每一次**
  `invoke`（只记 api 名、`err_msg` 和顶层 key 名，不记值）。Linux 上那个 `err_msg` 字符串就
  是这么找出来的。
