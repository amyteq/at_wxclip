  https://github.com/harrysun2006/WeChatVideoDownloader/blob/master/electron/decrypt.js

## 产品功能

- 开发一个 headless tool（with a light web server）and frontend as GUI
- 启动一个代理服务器并在 wechat for Linux app 中设置使用此代理
- 这样在 wechat 中播放此视频就能捕捉到请求地址
- 再经过 decoder 来解析出真实的下载地址
- 这样通过本 python tool 可以直接下载视频（不走代理）
- 视频可以进一步做截屏，文字提取，总结等操作

## 主要技术栈

- main tech stack: python + javascript / typescript
  - assumption: wechat running on linux box
  - python: implement a proxy server so we can capture the target links; also implement a
    server to serve admin and download dashboard
  - javascript: some frontend pages, also to decode the actual address of video contents

## 与参考实现核对后的更正（2026-09-11）

已逐行读过 `harrysun2006/WeChatVideoDownloader`（v2.0.1，上游 lecepin）的
`electron/` 全部代码，并在本机用纯 Node v24 跑过 `decrypt.js`。上面讨论原文里有两处
与代码不符，**以代码为准**：

1. **「再经过 decoder 来解析出真实的下载地址」** —— 不对。下载地址不需要解析，它直接来自
   JSAPI 响应里的 `media[0].url + media[0].url_token`。`decrypt.js` 做的是另一件事：用
   `decode_key` 生成 keystream，**解密已下载文件的头部**。decoder 在下载之后，不在下载之前。
2. **「在 wechat 中播放此视频就能捕捉到请求地址」** —— 不够。光有地址下载到的文件前
   128 KiB 是密文。参考实现之所以要注入脚本，就是因为 `decode_key` 不出现在任何网络请求
   里，只出现在 `WeixinJSBridge` 的 JSAPI 响应中。

### 参考实现的真实流程

| 步骤 | 代码位置 | 做什么 |
|------|----------|--------|
| 代理 | `electron/proxyServer.js` | `hoxy` MITM 代理，带自签 CA（`public/keys/`） |
| 注入点 1 | 同上，`channels.weixin.qq.com` | 改写 `/web/pages/feed` 响应，在 `</body>` 前插入 `<script src="//res.wx.qq.com/.../wvds.inject.js">` |
| 注入点 2 | 同上，`res.wx.qq.com` | 该脚本 URL 的响应体被整体替换成自己的 `injection_script` |
| 抓取 | 注入脚本 | hook `window.WeixinJSBridge.invoke`，在回调里筛 `err_msg` 含 `H5ExtTransfer:ok`（Win）/ `finderH5ExtTransfer:ok`（Mac），解析 `jsapi_resp.resp_json` 取 `object.object_desc.media[0]` 的 `decode_key`、`url`、`url_token`、`file_size`，外加 `description` 与 `nickname` |
| 回传 | 注入脚本 → 代理 | POST 到哨兵域名 `https://aaaa.com`，代理以 `phase:'request'` 拦下并经 IPC `VIDEO_CAPTURE` 交给界面 |
| 下载 | `electron/utils.js` | `axios.get(url, {responseType:'stream'})` + 桌面版 Chrome UA，**不走代理** |
| 解密 | `electron/utils.js` + `decrypt.js` | 流经 `xorTransform`：前 `131072` 字节与 keystream 逐字节 XOR，其后原样透传，写入 `<savePath>/<fileName>.mp4` |
| CA 安装 | `electron/cert.js` | Windows 用 `w_c.exe -c -add ... -s root`；macOS 把 `sudo security add-trusted-cert` 命令复制到剪贴板让人手动执行 |
| 代理设置 | `electron/setProxy.js` | macOS `networksetup -setsecurewebproxy`；否则写 Windows 注册表 `HKCU\...\Internet Settings`。**没有 Linux 分支** |

### `decrypt.js` 实测结论

- 它是 **Emscripten 产物**，5.2 MB，wasm 以 base64 内嵌在 `wasmData` 变量里
  （`wasmBinaryFile` 为空），`ENVIRONMENT_IS_NODE = true`，只导出一个
  `getDecryptionArray`。
- 内部：`new Module.WxIsaac64(seed)` → `.generate(131072)` → 取出 heap 上的字节并
  **reverse()** 后返回 `Uint8Array`。即 **ISAAC64 keystream，131072 字节（128 KiB）**。
- **可以脱离 Electron**：在纯 Node v24 里 import 即用，无任何 Electron 依赖。
- 运行时是**异步初始化**的：import 后立刻调用会抛
  `Module.WxIsaac64 is not a constructor`，要等运行时就绪（等待或挂
  `onRuntimeInitialized`）。
- **seed 必须是字符串**：wasm 侧签名是 `std::string`，传 number 直接抛
  `Cannot pass non-string to std::string`。
- **精度陷阱**：`decode_key` 是 64 位整数，一旦被当成 JS number 解析就会静默丢精度。
  实测 `"13835058055282163712"` 与 number 化后的 `"13835058055282164000"` 生成的
  keystream 毫无关系，且不会报错。全程当字符串传。
- 同一 seed 输出确定、不同 seed 输出不同，可以作为移植到 Python 的黄金样本。

## 本机 Linux 客户端的实测形态（2026-09-11，M0）

`flatpak info com.tencent.WeChat` + `pgrep -af wechat` 看到的：

- WeChat 是 **Flatpak 包**：`com.tencent.WeChat` 4.0.1.11，runtime
  `org.freedesktop.Platform 25.08`；沙箱权限只有 `shared=ipc;network`、`sockets=pulseaudio;x11`、
  `filesystems=xdg-download:ro`。**它没有宿主机家目录的访问权**，HOME 实际落在
  `~/.var/app/com.tencent.WeChat/`。同机还装了 `wechat-bin`（`/opt/wechat`），当前运行的是
  Flatpak 那个。
- 视频号相关的渲染跑在 `RadiumWMPF/runtime/WeChatAppEx` 这组进程里，进程参数是 Chromium 的
  （`network.mojom.NetworkService`、`gpu-process`、`--enable-features=...`），
  UA 片段为 `MicroMessenger/7.0.20.1781(0x6700143B) ... UnifiedPCLinuxWechat(0xf274010b)`。
  **即 webview 是 Chromium 内核**，这是注入路线在 Linux 上还有戏的原因。
- 因此 CA 的信任位置和 Win/Mac 都不一样。Flatpak 沙箱的 `/etc/pki` 来自 runtime 自带的证书包，
  **宿主机 `update-ca-trust` 装进去的 CA 它看不到**；`scripts/trust-ca.sh` 覆盖了沙箱 NSS /
  用户 NSS / 系统信任库三处，这对**主进程**有效。
  但 webview 不吃这一套 —— 它的根证书是编译在二进制里的，见下面那一节。
- **应用内代理设置可用**（issue #4 的截图）。Flatpak 默认 `shared=network`，和宿主机共享网络
  命名空间，所以沙箱内的 `127.0.0.1:8899` 就是宿主机上的代理。**但它只作用于主进程**：
  `WeChatAppEx` 的 renderer 进程既无 `--proxy-server` 参数也无 proxy 环境变量，webview 直连
  （2026-09-11 实测，下面第 2 条）。
- 主进程的网络长这样：`sgshort.wechat.com:80` 上大量 `POST /mmtls/<id>`（mmtls 套在 HTTP 里，
  body 不可读），加上 `wx.qlogo.cn`、`mmhead.c2c.wechat.com`、`dl.wechat.com`、`inews.gtimg.com`
  的普通 HTTPS。**host 是 `*.wechat.com`，不是参考实现那套 `*.weixin.qq.com`。**
- **本地 CA 会被接受**：上面那些 HTTPS 全部被成功 MITM 出明文，一次 TLS 失败都没有
  （CA 装在沙箱内的 NSS 库里，见 `scripts/trust-ca.sh`）。注意这说的是**主进程**；webview 的
  证书校验是另一条路，见下。
- **Flatpak 家目录只持久化 metadata 列出的子目录**：WeChat 是 `.xwechat` 和 `xwechat_files`。
  往 `~/.var/app/com.tencent.WeChat/.pki/nssdb` 写证书**不会**被应用看到，因为沙箱里的
  `$HOME/.pki` 压根没挂载。必须 `flatpak override --user com.tencent.WeChat --persist=.pki`。
  这个坑完全静默：certutil 全部成功，应用照样报 `tls alert certificate unknown`
  （webview 上显示「您的连接不是私密连接」）。
- **webview 的代理只能靠环境变量**：应用内设置管不到它，`flatpak override --env=http_proxy=…`
  之后 renderer 进程才带上代理（2026-09-11 实测，进程 environ 里能看到）。桌面图标/托盘启动
  走的是 systemd app scope，终端里 `flatpak run --env=…` 那一次性写法对它无效，所以要用
  override。

### webview 的证书校验：根证书编译在二进制里（2026-09-11 定论）

第二轮把 webview 塞进代理之后，页面仍然报「您的连接不是私密连接」，代理侧是
`Client TLS handshake failed … does not trust the proxy's certificate`。把三处信任库都装上、
并用 `--persist=.pki` 确认沙箱里能看到 `cert9.db` 之后依然如此。逐项排查的结论是
**这条路走不通，而且是设计如此**：

- `WeChatAppEx` 是 **Chromium 122.0.6261.156**（2024-12 构建），二进制里带着
  `Chrome Root Store`、`chrome_root_store` 以及一批公共根 CA 的名字
  （`DigiCert Global Root`、`GlobalSign Root CA`、`ISRG Root X1` …）——
  **它自带一份根证书列表**。
- 真正做校验的那个进程**从来没打开过 NSS 数据库**：
  `network.mojom.NetworkService` 进程的 `/proc/<pid>/maps` 里只有 `libnss3`/`libnssutil3`，
  **没有 `libsoftokn3`（sql 数据库后端）也没有 `libnssckbi`（内置根模块）**。
  只有 browser 进程加载了完整的 NSS 栈并打开着 `$HOME/.pki/nssdb/{cert9,key4}.db`
  （那是给客户端证书用的）。
- 所以 `~/.pki/nssdb`、系统信任库、p11-kit（沙箱里 `libnssckbi.so → load-p11-kit-trust.so`）
  对 webview 全部无效。**Linux 上不存在「把 CA 装到某处让 webview 信任」的办法。**
- 证书本身没问题，已逐项排除：CA 指纹与代理实际签发的一致、叶证书 367 天（未超 Chromium 的
  398 天上限）、SAN 与 EKU 正确。
- 参考实现在 Win/Mac 能成，是因为 Chromium 在那两个平台上会去查操作系统的信任库；
  换成自带根证书列表的构建就不会。

**出路是 `--ignore-certificate-errors-spki-list=<base64(sha256(SPKI))>`**：这个 switch 在
二进制里存在，只放行我们这一个公钥，比整体关掉证书校验窄得多。但 webview 的命令行是
`RadiumWMPF/host/libwmpf_host_export.so` 拼的，它不读任何环境变量或配置文件来追加参数
（上面那些 switch 名字在这个 .so 里一个都搜不到），所以只能在 exec 的那一刻插进去 ——
这就是 `scripts/appex-flags-preload.c`（LD_PRELOAD 钩 `execv`/`execve`/`execvp`/`posix_spawn`，
只对程序名为 `WeChatAppEx` 的 exec 追加参数，并且不重复追加）。

**已实测生效**（2026-09-11 15:01 重启后）：`--ignore-certificate-errors-spki-list=<我们的 SPKI>`
同时出现在 browser 进程和 `network.mojom.NetworkService` 进程的 cmdline 里，视频号页面正常打开，
注入脚本落地，`decode_key` 拿到手。

顺带记下两件事：WeChat **不在磁盘上留视频缓存**（播完一段后在 `~/xwechat_files`、`~/.xwechat`
里找不到任何近期写入的大文件），所以没有「直接读缓存文件」这条捷径；`--remote-debugging-port`
在二进制里也存在，同一个 LD_PRELOAD 机制可以打开它，届时能用 CDP 直接注入、完全不需要 MITM，
但那会开一个调试端口，非必要不开。

## 待确认的前提

以下几点会直接影响设计，动手前先确认（M0 spike 的内容，操作步骤见 `docs/M0-操作步骤.md`）：

1. ~~**Linux 版 WeChat 能不能被 MITM**~~ —— **分两半，已确认**（2026-09-11）。
   **主进程可以**：应用内代理设置生效，CA 装进 Flatpak 沙箱的 NSS 库后客户端接受本地证书，
   HTTPS 被解出明文。**webview 不行 —— 靠装 CA 永远不行**，它的根证书编译在二进制里
   （见上一节），只能用 `--ignore-certificate-errors-spki-list` 放行我们的公钥。
2. ~~**Linux 客户端的视频号是不是同一条 H5 路径**~~ —— **已确认是**，而且 URL 与参考实现一致：
   webview 打开过
   `https://channels.weixin.qq.com/web/pages/feed?oid=…&nid=…&context_id=…&entrance_id=1002&exportkey=…`，
   标题「视频号」，并落了 `channels.weixin.qq.com` 的 cookie。证据是 WeChat 自己的 Chromium
   profile：`~/.var/app/com.tencent.WeChat/.xwechat/radium/web/profiles/multitab_<hash>/{History,Cookies}`。
   **这意味着注入路线在 Linux 上成立，项目性质不变（M）。**
3. ~~**怎么把 webview 也塞进代理**~~ —— **已确认：环境变量可行**。`flatpak override --env=http_proxy=…`
   之后 webview 确实来连代理（代理日志里出现了 `channels.weixin.qq.com`、`mp.weixin.qq.com` 的
   TLS 握手尝试）。注意桌面图标/托盘启动走 systemd app scope，`flatpak run --env=…` 那种一次性
   写法对它无效，必须用 override。路由通了以后卡住的是证书信任，那是上一节的事。
4. ~~**页面进得去之后，`window.WeixinJSBridge` 在不在、可不可 hook**~~ —— **已确认，在且可 hook**
   （2026-09-11）。回传的 `probe` 里 `has_bridge: true`、`hooked: true`，`hook` 里
   `has_invoke: true`、`has_on: true`。注入进的是
   `channels.weixin.qq.com/web/pages/home`。
5. ~~**`err_msg` 在 Linux 上的字符串**~~ —— **已记录，是个混血**（2026-09-11）：api 名跟 macOS 一样
   是 `finderH5ExtTransfer`，而 `err_msg` 跟 Windows 一样是 `H5ExtTransfer:ok`。对得上 UA 里
   同时出现 `WindowsWechat` 和 `UnifiedPCLinuxWechat`。脱敏样本见
   `evals/jsapi-response-linux-20260911.md`。
   另外 `decode_key` 在 Linux 上是**带引号的字符串**、**8–10 位**十进制
   （不是参考实现样本里那种 20 位 64 位整数），62/62 条都是。防护不撤：换回裸数字就会静默丢精度。
6. **QUIC/HTTP3 会不会绕过 HTTP 代理** —— Chromium 内核有这个可能，代理侧只能靠
   `captures/traffic-*.jsonl` 里 host 异常稀少来发现。
7. ~~**视频在 xrdp 下能不能播**~~ —— **能播**（2026-09-11 重启 WeChat 后实测）。第一轮播不出来
   大概率是代理把主进程的 mmtls 长连接（`*.wechat.com`）也拦了，现在这些 host 进了
   `DEFAULT_IGNORE_HOSTS`，并且大 body 改为流式转发。纯软件渲染
   （`--use-gl=angle --use-angle=swiftshader-webgl`）不影响播放。
8. ~~**媒体是整段文件还是分片**~~ —— **整段文件，已实测跑通**（2026-09-11）。`media[]` 每条给一个
   `download_url`（`url` + `url_token`）和 `file_size`，没有 m3u8/m4s 清单；下载字节数与
   `file_size` 完全一致，XOR 掉前 128 KiB 后是标准 `ftyp`/`isom` 头，`ffprobe` 认出
   h264 1080x2344 + aac 7.48s，`ffmpeg -f null -` 全解零报错。
   注意一个 `capture` 事件里 `media[]` 有多条（本次每次 8 条），`file_size` 跨度 3.8 MB–585 MB，
   所以下载要流式 + 进度，不能整块读进内存。
9. 截屏与文字提取的落地方式（ffmpeg + OCR 引擎）与是否需要本地模型。
